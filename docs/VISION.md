# Project Basilisk — 核心优势与愿景

> **一门可以在编译时决定「要不要 GC」的系统语言——同一份源码，既能跑出 C++ 的确定性，也能跑出 Go 的开发效率。**
> 整套工具链从第一行汇编自举而来，不欠任何第三方编译器一行代码。

语言名：**Ember**。工具链名：**Basilisk**。
本文档回答两个问题：**用户为什么要用这套东西？工程师凭什么愿意上手？**

---

## 一、运行时层面（对最终用户）

### 双模内存管理，一键切换 ★ 全场唯一稀缺卖点

同一套 Ember 源码，编译时通过构建文件声明 `gc = true / false`：

| 模式 | 行为 | 对标 |
|---|---|---|
| `gc = false` | 手动管理，借用检查器**强制执行**生命周期保护 | C++ 的控制 + Rust 的安全 |
| `gc = true`  | 分代自动回收，借用检查器**只报警不阻断** | JVM / Go 的开发效率 |

**渐进式安全**是这套设计的灵魂：安全带始终在车上，你决定什么时候系。
原型期开 GC 快速迭代，热路径切手动模式接受完整借用检查——一个项目，两种生态，
类型系统始终一致，不需要重学语言。

> ⚠️ 已知风险与对策：双模最大的工程隐患是标准库沿内存模式分裂（参照 D 语言
> `@nogc` 的教训）。Basilisk 的答案是卫生宏 + `#[cfg(gc)] / #[cfg(manual)]`
> 条件编译，**标准库自身通过宏实现双模适配**（见第四节），从第一天起杜绝两套生态。

### 见闻即所得（可预测的机器码）

你写的 Ember 源码，在不同模式下编译出的机器码**差异有迹可循**：手动模式多
`free` 调用，GC 模式多写屏障——仅此而已。不做"魔法优化"，不在你背后插入
看不见的运行时行为。这正是 C 程序员不信任 GC 语言的根源，Basilisk 直接解掉它。

### 零运行时依赖

最终产物是纯 ARM64 机器码：不依赖 libc、不依赖 JVM、不依赖任何动态链接库。
**这不是承诺，是第一阶段已实测的事实**：种子编译器 `nm -u` 零未定义符号，
`-lSystem` 仅为 macOS dyld 的挂载要求，未调用其中任何函数。后续可移植到裸金属。

### 确定性性能

手动模式下所有内存操作在编译期决定：无 GC 暂停、无运行时突发卡顿。
适合高频交易、游戏引擎、实时系统。

## 二、工程与运维层面（对开发者）

### 自举工具链，无需第三方编译器

自举完成后，构建整个项目只需系统自带的 `as` + `ld`——不需要 Xcode、Clang、GCC。
当前种子编译器的构建流程已经做到了这一点（`build.sh` 全程只碰 `as` 和 `ld`）。

### 内存分配完全掌控

编译器自身的内存由 HeapForge 管理（纯 ARM64 汇编实现，4100+ 断言保障）。
编译器不会因为 malloc 实现差异在另一台机器上行为不同——内存在你的眼皮底下流动。
AST 节点走位图块池，I/O 缓冲走线性栈分配器，分配策略按数据生命周期精确选型。

### 可审计、可调试的底层

编译器前端（词法/语法/类型推导）用 Ember 编写，后端用汇编，没有黑盒依赖。
出 Bug 时可以一路追到机器码层面。

### 跨架构的基础

移植到 x86_64 / RISC-V = **重写代码生成后端 + 5 个系统调用存根，前端零改动**。
词法、语法、类型推导、优化全部架构无关。

## 三、性能与优化层面（对性能追求者）

> 本节各项均标注路线图阶段，与「已兑现」严格区分。

| 优点 | 说明 | 阶段 |

| 编译期单态化 | 泛型在编译期展开为具体类型实例，零虚表开销 | 第三阶段起 |

## 四、审美与控制层面（对语言设计爱好者）

### 正交融合的语法

取 Rust 的模式匹配和生命周期标注、C++ 的模板和 RAII、Go 的轻量级协程语法，
融合成一套统一、无割裂感的语法——每个特性正交存在，不为兼容历史付税。

### 严谨的类型系统

Hindley-Milner 类型推导 + Trait 约束 + 生命周期标注。
**无论 GC 开或关，类型系统始终一致**——内存模式改变不需要重学语言。

### 卫生宏与条件编译

Hygienic Macro，编译期代码生成，支持 `#[cfg(gc)]` / `#[cfg(manual)]`。
标准库本身通过宏实现双模适配（呼应第一节的生态分裂对策）。
